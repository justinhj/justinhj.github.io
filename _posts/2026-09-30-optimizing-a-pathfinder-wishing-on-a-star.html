Background

Almost 30 years ago I wrote an A* algorithm tutorial and published it (on GeoCities I think), and it got a decent amount of traffic. Although the focus was on pseudocode and how the algorithm worked, I received a lot of requests for source code, and so I shared an implementation in C++ that was reasonably optimized so that it could be used in real systems, without being so complex that it became unsuitable for students. You can find it here: justinhj/astar-algorithm-cpp Although there are better tutorials around these days, the code has endured quite well; it has been used by robotics researchers and video game developers, as well as being used by universities and colleges as a clear but efficient implementation. Thanks to C++'s backwards compatibility, that code mostly works unchanged from the early 2000s version, although there have been some minor bug fixes over the years from helpful contributors. The first breaking change came with version 1.2 where we changed the closed list to an unordered_set (now it requires the user to provide a hash function for their data type). At the end of 2025, I updated the code to require C++11 as the minimum version so I could make some changes in the name of modernization, and I added unit tests with doctest.

Musing on A-Star

Last week I was randomly checking out Muse, Meta's new personal AI agent, and decided to point it to one of my oldest GitHub repos justinhj/astar-algorithm-cpp and ask what it thought. The analysis was surprisingly good; whilst the agent politely acknowledged some strengths of the repo, it also noticed some simple data structure changes to improve performance.

What was good already (in Muse's review):

  1. I wrap the user's UserNode type in a template, the main interface to the API, and the user implements the required functionality for their problem. This means no vtable, no virtual dispatch in the successor-expansion hot loop, and no pointer chasing. It means for multiple node types you pay in executable size and instruction cache for the extra code, but in most applications the number of node types is small.
  2. Efficient and fast memory use with the provided "fixed-size allocator", a fixed-size pool of nodes. It is very fast, but single-threaded, and requires you to have a bound on your maximum number of search nodes. In modern C++ you could replace this with std::pmr::unsynchronized_pool_resource, which has a little extra overhead but is growable. It would also require C++17.
  3. Incremental state-machine-style API is easy to understand and use. For game developers in the '90s it was rarely possible to do a search in a single frame. You may want to spread it across multiple frames, and for that you need to be able to control the search step by step. This is also handy for people learning the algorithm and building visualizations around its progress.

Muse came up with a number of minor issues but also ideas around optimizing the bottlenecks and potential memory issues in certain use cases.

  1. Open-list membership is still a linear scan. The agent identified the biggest open performance bottleneck, and recommended using an std::unordered_set like we use for the closed list, but in conjunction with the existing heap so we still have fast best-node popping.
  2. Issues around double-free and management of fsa.h between runs that were worth fixing.

I copied Muse's feedback into Antigravity and worked with Gemini Flash (3.8) to make a series of optimizations which added up to over a 22x increase in speed.

Open list and Closed list access patterns

In A*, the open list tracks nodes that have been discovered and evaluated but not yet expanded. We have estimated how close to the goal they are with the user-supplied heuristic, plus the lowest cost of getting to this node so far. It is the boundary between the known territory and the undiscovered graph. The closed list tracks nodes that have been fully explored.

Each list has its own access patterns, and so the choice of data structure should reflect that.

Open list access patterns

Pop the best node - based on cost and estimated distance to goal, we need to get the next best candidate. Insert new node - we add the start node or each new candidate to the open list. Membership check - is a node in the open list? Decrease cost - update an existing node when a cheaper way there is found.

Closed list access patterns

Insert a node - adding an expanded node to the closed list. Membership check - is this node already expanded? Reopen - we move a node from Closed to Open. (This happens only when the heuristic is not consistent, see below).

Baseline architecture

As pointed out by Muse, the existing architecture has a couple of bottlenecks we can work on. 

std::vector<Node*> m_OpenList;
std::unordered_set<Node*, NodeHash, NodeEqual> m_ClosedList;

Note that "Pop the best node" from Open is O(log n) and "Membership check" on Closed is O(1) average… great! But the open list has the two O(n) bottlenecks.

  1. Membership check. (Linear scan).
  2. Decrease cost. (Rebuild the heap).

That aligns with what Muse suggested and so I began the task of optimizing these Open list bottlenecks.

Optimization step 1 - Introduce an auxiliary lookup set alongside the heap

It's quite common that when a single data structure does not meet the runtime characteristics we want for its access patterns, we simply use two data structures. We see this with database tables and indexes (every write has to go to the rows in the table and the index), and LRU caches (a hash map for lookup and a doubly-linked list for recency). The Boost Multi-Index Containers Library provides a performant general way to combine multiple indices with different sorting and access semantics. Rather than introduce a dependency on Boost, we will simply implement what we need by hand.

In this case, the suggestion was to add an std::unordered_set to live alongside the heap. The code changes are minimal: whenever a node is added to or removed from m_OpenList (the heap), it is also added to or removed from the new m_OpenSet. The linear search is removed and replaced with a set lookup. 

std::vector<Node*> m_OpenList; // Kept as the priority queue
std::unordered_set<Node*, NodeHash, NodeEqual> m_OpenSet; // New auxiliary set
std::unordered_set<Node*, NodeHash, NodeEqual> m_ClosedList; // Same

The benchmark result is an incredible +249.0% faster (from 302s down to 86s).

Optimization step 2 - Intrusive min-heap

Once the first optimization was tested and benched, I resumed working with the agent on the next bottleneck: decreasing key scores when better nodes are found on the open list. In the baseline implementation, when a cheaper path to an open node is found, we must update its cost. This should be an O(log n) complexity operation, but unfortunately C++ heaps do not have a way to adjust the location of an item in the heap when its sort key changes. This is why in the original code you see the call to make_heap, which is O(n). 

// ...
else if (openlist_result != m_OpenSet.end()) {
    // Update open node with successor node AStar data
    //*(*openlist_result) = *(*successor);
    (*openlist_result)->parent = (*successor)->parent;
    (*openlist_result)->g = (*successor)->g;
    (*openlist_result)->h = (*successor)->h;
    (*openlist_result)->f = (*successor)->f;

    // Free successor node
    FreeNode((*successor));

    // re-make the heap O(n)
    make_heap(m_OpenList.begin(), m_OpenList.end(), HeapCompare_f());
}

Our open list is just a vector of elements, implicitly laid out like a tree. In order to satisfy the heap property, every element must be smaller than both its children. The make_heap function uses Floyd's Heap Construction Algorithm, which is a very clever piece of work, but even so, is O(n) when we can do better.

The code adds utility functions: swapNodes so we can manipulate the tree, and siftUp~/~siftDown that take care of moving items up or down through the heap until the heap property is satisfied. To ensure there are no mistakes, the agent also wrote a function to run when asserts are on: AssertHeapInvariants.

Now when we decrease the cost of a key, we know where it is in the heap from its heap_index, then we call siftUp (it goes higher up the tree because it's a min-heap and its value has decreased). The number of levels to sift up is constrained by the tree depth, which is what gives us the O(log n) runtime.

When popping the minimum, we can also cheaply replace it by taking the tail (the last element in the vector), putting it at the root of the tree (index 0), and calling siftDown to move it if needed to the right place.

Benching this new method reveals the algorithm is now +1375.2% faster than our original code (from 302s down to 20s).

Optimization step 3 - Unified node map & deferred allocations

In this third and final (for now) pass, we will get an even more substantial speedup by continuing to optimize the open and closed lists, primarily, but also by some adjustments to how new nodes are allocated.

  1. Avoiding the New Node tax.
  2. Unifying the Open Set and Closed List into a single m_NodeMap.
  3. Repurposing heap_index as an implicit state discriminator (Open vs. Closed).

Avoiding the New Node tax

For each new successor in the search we do the following:

  1. Allocate a node.
  2. Look for the node on the open list.
  3. If not there, look for the node on the closed list.
  4. If the node was already explored or had a worse cost, it is deallocated immediately.

On the sample problem of finding a path in a grid, we waste a lot of time looking at nodes that have already been explored, so this allocation and deallocation is overhead it would be nice to remove.

The user code would handle adding a successor and my code would put them in a vector m_Successors which can be iterated over and processed as above. We can process a node fully at the time it is added with some rearrangement of my code. After that, no allocation is done until we know the node is needed.

Instead of buffering successors in m_Successors, SearchStep() exposes the current node being expanded (m_CurrentExpandingNode). When the user calls AddSuccessor(state), we construct a temporary probe node directly on the stack (Node dummy; dummy.m_UserState = state;) and query m_NodeMap. Only if the state is genuinely unvisited do we call AllocateNode().

Unifying the Open Set and Closed List into a single m_NodeMap

Let's recap the three containers in use after the last two steps and review the work needed to generate each successor: 

m_OpenList (std::vector<Node*>); //  Min-heap priority queue.
m_OpenSet (std::unordered_set<Node*>); //  Fast membership test for Open.
m_ClosedList (std::unordered_set<Node*>); //  Fast membership test for Closed.

Instead of having a set for open and a set for closed, the insight is that we can combine the two sets together since a node can only be open or closed. That way we can do a single lookup instead of two. 

// Stores every node currently discovered (whether Open or Closed)
std::unordered_set<Node*, NodeHash, NodeEqual> m_NodeMap;

Repurposing heap_index as an implicit state discriminator (Open vs. Closed)

We already added heap_index to the node that identifies its position in the priority queue. We can set heap_index to some constant (SIZE_MAX) to indicate that the node is closed, and that saves us from having to use up more memory to add a flag indicating the node's status.

These two data structure changes make operations simpler and more efficient. For example: 

Node* n = m_OpenList.front();
swapNodes(0, m_OpenList.size() - 1); // Now the tail of the open list is at the front
m_OpenList.pop_back(); 
n->heap_index = SIZE_MAX; // Conceptually, removes from open and adds to closed

if (!m_OpenList.empty()) {
  siftDown(0); // We need to fix the heap by moving the new front node
}

Furthermore, because our grid heuristic is consistent (monotonic) 1, closed nodes are guaranteed optimal; if a probe reveals heap_index == SIZE_MAX, we can skip it immediately.

Comparing with more realistic search sizes

A 1,000 x 1,000 open-grid search is a brutal stress test that intentionally blows up the frontier to expose asymptotic bottlenecks. But in real-world applications (like video games or robotics), pathfinding is rarely done across 1,000,000 raw grid cells in a single frame. Usually, games use hierarchical pathfinding for long distances, and local A* searches are restricted to tactical ranges (e.g., 64x64 tiles or graph edges).

Do these algorithmic optimizations still make sense when the frontier is small?

To test this, I modified the benchmark with MAX_SEARCH_DISTANCE = 64, constraining the random start and goal pairs to be within 64 grid squares horizontally and vertically of each other on the 1,000x1,000 map.

Here are the results for 1,000 searches across 5 runs:

Commit Description Mean Runtime Throughput vs Baseline Speedup Factor
64bdb20 Baseline (Pre-optimization) 45.3353 s — 1.00x
7424a4c Step 1: Open set lookup O(1) 48.3634 s -6.3% (Slower!) 0.94x
3ee685b Step 2: Intrusive min-heap 44.4163 s +2.1% 1.02x
a37013f Step 3: Unified map & deferred alloc 23.7850 s +90.6% faster 1.91x

When O(N) Beats O(1)

You can see that in Step 1, introducing m_OpenSet actually made short searches 6% slower.

When a search is bounded to 64 tiles, the open list is small (often just a few dozen nodes) and we are scanning a contiguous array of pointers in a std::vector that is most likely in the cache. By contrast, computing a hash, traversing bucket chains, and dealing with cache misses in std::unordered_set introduces a fixed overhead that isn't worth paying when N is small.

Similarly, in Step 2, std::make_heap was operating on such tiny vectors that replacing it with an intrusive heap barely moved the needle (1.02x vs baseline).

Step 3 Still Wins

However, Step 3 (a37013f) still cut the runtime almost in half (1.91x speedup, down to 23.78 s).

Why? Because avoiding redundant memory allocations is a universal win. On a 4-connected grid, roughly 3 out of 4 evaluated neighbors are duplicates. Probing on the stack and only calling AllocateNode() when a node is genuinely new eliminates thousands of pool/heap allocations regardless of how long the path is.

Conclusion and thoughts

These optimizations are nice, high-level changes that rely on more efficient data structures. I expect that I can get more performance by continuing to iterate over the bottlenecks; however, I am done for the time being. This repository has tried to meet two goals: 1) an easy-to-understand implementation that maps to the pseudocode of the algorithm and 2) a fast and memory-efficient implementation suitable for real-time systems like robotics and video games. Once you head down the path of optimization, the code will become more difficult to follow and more detached from the textbook implementation. See this X Post by Dmitrii Kovanikov for a similar sentiment.

Although these steps are currently on the master branch of the project, I expect that as I continue to make more optimizations, I will likely make multiple branches available such that the user can match the version to their goal, whether it be learning or pathfinding with different expectations around performance and memory use.

1

An admissible heuristic never overestimates the actual cost to the goal (h(n) <= h*(n)), which guarantees A* finds the optimal shortest path. A monotonic (or consistent) heuristic adds the triangle inequality condition: for any node A and successor B, h(A) <= cost(A, B) + h(B). Monotonicity ensures that f-scores are non- decreasing along any path, guaranteeing that the first time a node is expanded into the Closed list, its optimal distance from the start is already finalized. Consequently, under a monotonic heuristic (which includes standard grid metrics like Manhattan and Euclidean distance), nodes on the Closed list never need to be reopened.
